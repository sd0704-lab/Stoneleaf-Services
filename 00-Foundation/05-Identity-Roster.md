# Stoneleaf Services — Identity Roster

**No Stone Left Unturned**

## Purpose

This document establishes the synthetic employee identity roster for the Stoneleaf Services simulated organization.

The roster provides a consistent organizational identity dataset for future:

- Active Directory
- Microsoft Entra ID
- Role-Based Access Control (RBAC)
- Security groups
- Organizational Units (OUs)
- Group Policy
- Workstation assignments
- Security monitoring
- Employee lifecycle exercises
- Incident response
- Digital investigations
- Intelligence exercises
- Troubleshooting
- Access-control testing

Stoneleaf Services initially consists of **40 synthetic employee identities**.

All names, employee records, positions, and organizational relationships contained in this document are fictional and exist exclusively for the Stoneleaf Services lab, educational, training, and portfolio environment.

---

# Identity Standards

Each simulated employee receives:

- Unique employee ID
- First and last name
- Job title
- Department
- Manager
- Standard username
- Privilege classification
- Administrative-account designation where applicable

Additional identity attributes will be added as the corresponding architecture is designed.

---

# Employee ID Standard

Employee IDs use the following format:

`SLS-####`

The initial workforce occupies:

`SLS-1001` through `SLS-1040`

Employee IDs are permanent identity references and must not be reused.

---

# Username Standard

Standard employee usernames use:

`first.last`

Example:

`olivia.bennett`

Privileged administrative accounts, when required, use:

`adm-first.last`

Example:

`adm-olivia.bennett`

Administrative accounts remain separate from normal employee accounts.

# Access-Control Model

Stoneleaf Services will generally use the following access-control relationship:

`Employee → Role → Security Group → Resource Permission`

Example:

`Gabriel Torres → Digital Investigator → SG-ROLE-Investigators → SG-RES-Investigations-RW → Investigation Resources`

Permissions should be assigned through groups rather than directly to individual users whenever practical.

This provides a foundation for implementing and demonstrating Role-Based Access Control.

---

# Separation of Duties

The identity structure is intentionally designed to create different access requirements.

Examples include:

- Executive authority does not automatically provide technical administrative privileges.
- IT administrators may administer infrastructure without automatically receiving access to HR, legal, investigation, or intelligence records.
- Cybersecurity personnel may receive security-monitoring privileges without unrestricted access to all business data.
- Digital investigators may access investigation resources without becoming general infrastructure administrators.
- Intelligence analysts may access intelligence resources without receiving unrelated administrative privileges.
- Human Resources personnel may access protected personnel information without receiving access to investigation or security-administration resources.
- Legal & Compliance personnel may access legal, policy, compliance, and risk information without receiving general infrastructure-administration privileges.
- Support personnel may receive delegated capabilities without receiving unrestricted administrative rights.

These distinctions will later be enforced through security groups, permissions, administrative delegation, and other access controls.

# Employee Lifecycle

The roster will support simulated Joiner, Mover, and Leaver processes.

## Joiner

A new employee may require:

- Employee identity creation
- Active Directory account
- Username
- UPN
- Organizational email
- Department assignment
- Manager assignment
- Security-group membership
- Resource permissions
- Workstation assignment
- Application access

## Mover

An employee changing roles may require:

- Job-title update
- Department update
- Manager update
- Group-membership review
- Permission changes
- Privileged-access review
- Resource-access changes
- Workstation reassignment

Existing permissions should be reviewed rather than simply adding the permissions associated with the employee's new position.

## Leaver

An employee leaving the organization may require:

- Account disablement
- Active-session revocation
- Privileged-account disablement
- Security-group removal
- Resource-access removal
- Device reassignment
- Data preservation
- Mail or file reassignment where appropriate
- Event documentation

- Passwords
- Password hashes
- MFA secrets
- Authentication tokens
- API keys
- Private keys
- Recovery credentials
- Other authentication secrets
